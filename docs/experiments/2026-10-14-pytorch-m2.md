# M2 protocol and cache lifecycle validation

Date: 2026-10-14. The M2 gate passed on the laptop's isolated CPU runtime.
This validates protocol behavior and model equivalence in one process, including
loopback RPC. It does not demonstrate three remote worker services, useful stage
overlap or Internet performance. See the [protocol guide](../PYTORCH_PROTOCOL.md)
and [machine-readable evidence](2026-10-14-pytorch-m2-summary.json).

`33aec5e084dc12cef677821fcc8ca55a00f74298531f1a97d499658e6930254d`.

The host is the AMD Ryzen AI 9 HX 370 laptop with approximately 32 GiB RAM and
15.18 GiB available to the Docker VM. Docker Engine 29.8.2 / Compose 5.6.0 ran

containers remained running, and these runs are not performance comparisons.

## Checks and results

| Check | Observed result |
| --- | --- |
| Full final suite | 95 passed, zero failures, zero skips |
| Codec | Eight tests: exact little-endian round trips, finite values, bounded shape/byte counts and parsing |
| Transport | Seven tests: matching binary replies, identity/position validation, no retries, malformed/oversized messages and loopback restriction |
| Worker lifecycle | 27 tests, including actual gRPC caller cancellation during compute |
| Real-model protocol integration | Four tests; 41 recorded numerical comparisons |
| Maximum absolute logit difference | `1.9073486328125e-6`, below frozen `atol=1e-3, rtol=0` |
| Real-model cleanup | Zero active sessions, reserved positions and cache bytes after every integration case |
| Legacy dependency-free discovery | 38 passed; 57 opt-in model/protocol tests explicitly skipped |

The remaining 49 tests are the existing M0/M1 and benchmark/configuration checks.
Numerical tests compare every prefill-position logit for 1-, 128- and 1,024-token
prompts, followed by eight identical forced continuations. All three worker
handlers receive and return binary Protobuf messages. Each owns one loaded layer
slice and its independent caches; the test driver owns embeddings and the head.
A separate real-stage loopback gRPC check returns the same activations as the
serialized in-memory transport. Synthetic token fixtures and exact offsets are
fixed in the test source and recorded in the JSON evidence.

The driver recorded 120 successful stage Step messages with 1,020,672 activation
payload bytes sent and the same amount received. These counts cover the sequential
three-stage driver calls, excluding the separate lost-reply and loopback probes.
They count tensor payload bytes, not complete Protobuf frames, transport overhead,
bandwidth or throughput.

Malformed input tests reject oversized messages before parsing and inconsistent
tensor metadata/non-finite values before Torch allocation. Identity, boot, lease,
sequence, context and cache checks reject invalid requests without advancing another
session. Duplicate Opens return the same reservation; conflicting requests fail.
The tombstone test verifies that admission fails rather than evicting protected IDs.

Lifecycle tests use a fake monotonic clock and a compute thread blocked on an
explicit event. The cache is deliberately mutated before blocking. Close/cancel,
expiry, timeout and gRPC caller cancellation retain its reservation until the
thread is released, then discard late output and clear its cache. The suite also
checks periodic expiry without a new request, renewal bounded by the original
lifetime, failure isolation, and deadline expiry during result encoding.

A simulated unresponsive computation marks the handler not ready and requiring
restart after its grace period. Bounded shutdown returns false while that thread
still owns its cache. The tests then release the thread and verify cleanup. M2
does not kill or restart a worker process; M3 must provide that supervisor.

The lost-response case discards a successful Step response, resubmits its old
sequence, receives `OUT_OF_ORDER` and verifies the committed position did not
advance again. Another session remains correct. This proves rejection of duplicate
execution, not transparent recovery of the lost activation.

## Reproduction and retained evidence

These commands were executed successfully against the final implementation:

```powershell
docker compose -f compose.pytorch.yaml build prepare
docker compose -f compose.pytorch.yaml run --rm tests
```

The verified model/artifact volumes from M1 were reused. A fresh checkout also
needs `docker compose -f compose.pytorch.yaml run --rm prepare` before testing,
as documented in the runtime guide and already validated in M1.

The final suite reported 95 tests in 10.167 seconds. Its raw log is
`.lab/pytorch-results/m2-compose-tests-final.txt`, and its numerical observation
file is `20261014T143712828800Z-m2-validation.json`. Earlier observations
`20261014T143140575345Z-m2-validation.json` and
`20261014T143453533910Z-m2-validation.json` remain retained locally. All executed
test runs passed; no numerical failure was excluded and no tolerance was relaxed.
Expected injected failures are explicit passing assertions, not omitted runs.

The legacy discovery check used the unchanged `steamboat-net-lab:m1-regression`
image with current source mounted read-only and the M2 opt-in flag absent. It
confirms test discovery remains usable without the new Protobuf version; it does
not count skipped tests as M2 validation. The full M2 suite ran in the pinned
PyTorch image without skips. The linked JSON preserves test names, numerical
observations, bounds, runtime details and source hashes for this implementation.

## Limits and next gate

The 1 MiB message ceiling, eight-session and cache reservation bounds, operation
ordering, lease expiry and response validation are implemented. Compute uses one
thread per handler and rejects concurrent stage work; bounded stage queues remain
M3 work. A worker's cache-byte reading is marked inexact while its thread is active
and reports the last committed value. Peak RSS, allocator retention and temporary
loading memory were not measured.

M3 must serve the three fixed assignments in separate processes/containers and
add readiness, bounded queues, supervised shutdown and restart behavior. M4 owns
cross-worker admission/cleanup, client cancellation and independent-request
scheduling. No public admission, retry/replay recovery, WAN measurement or
pooled-memory benefit is claimed by this milestone.
