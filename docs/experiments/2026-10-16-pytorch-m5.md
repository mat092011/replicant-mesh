# M5 validation: standalone coordinator and private network lab

> Historical Replicant Mesh experiment, recorded before the project rename.
> Original image names, source paths and measurements are retained as evidence;
> use the [migration guide](../RENAMING.md) for current commands and names.

Date: 2026-10-16. The M5 implementation gate passes: a supervised coordinator
streams tokens to a thin client, schedules three fixed PyTorch workers, preserves
reference logits and reclaims sessions. The Docker experiment runner records
network conditions, failures and verified reset. All six runtime milestones
M0–M5 are implemented. The broader P3 performance envelope, separate-device
experiments and P4 pooled-memory demonstration remain incomplete.

See the [machine-readable summary](2026-10-16-pytorch-m5-summary.json),
[lab guide](../PYTORCH_LAB.md) and [implementation plan](../PYTORCH_PIPELINE_PLAN.md).
The implementation is the working tree above
`4cf0772ecfa8f490caf10391e9e43933a1152ef3` on `codex/pytorch-pipeline-plan`;
the summary identifies its source files by SHA-256. Subsequent P3/P4 preparation
tools are separate changes and are excluded from this M5 source inventory.

## Configuration and measurement boundaries

- AMD Ryzen AI 9 HX 370, 24 logical CPUs, approximately 32 GiB host RAM and
  15.18 GiB Docker VM RAM; Windows with Docker Desktop's WSL2 Linux engine.
- Docker Engine 29.8.2, Compose 5.6.0, Python 3.12.15, Torch 2.14.1+cpu,
  Transformers 5.19.0, grpcio 1.84.0, Protobuf 7.36.2, safetensors 0.8.0.
- `Maykeye/TinyLLama-v0` model and tokenizer revision
  `298338802ab94432b917bcce11382aa151aee50f`; float32, eager attention,
  unpadded batch size one, no activation compression, greedy fixed-length output
  with EOS ignored. Manifest fingerprint:
  `33aec5e084dc12cef677821fcc8ca55a00f74298531f1a97d499658e6930254d`.
- Worker layers `[0,3)`, `[3,6)`, `[6,8)`; coordinator owns tokenizer, embeddings,
  final normalization, output projection and token feedback. All activation
  exchanges pass through the coordinator.
- Each worker and coordinator has a two-CPU quota and 3 GiB memory ceiling;
  the thin driver has one CPU and 1 GiB. The reference/validation container has
  two CPUs and 6 GiB. Quotas are ceilings, not reserved cores.
- Private internal Docker network, no published ports, offline verified model
  artifacts. Only the four inference services have `NET_ADMIN`. The historical
  Petals containers remained stopped and are not part of this execution path.
- `tc` reports iproute2 6.1.0 and libbpf 1.1.2. Python dependencies and base image
  are pinned; the Debian package repository used to install iproute2 is not a
  frozen snapshot. Image identities and observed tool versions identify these runs.

Client timing uses one monotonic clock from RPC submission through token arrival;
TTFT includes admission and prefill. Tokenization and warm-up are excluded.
Throughput counts only generated tokens from completed requests. Failed attempts,
partial outputs and error codes are retained; no request or Step is automatically
retried. Server counters separate prefill/decode, scheduler wait, worker queue,
worker compute and RPC wall time. RPC already includes worker time: these are
overlapping measurements, not additive stages. Transfer and serialization remain
combined in the unexplained RPC remainder. Step byte counts omit transport framing
and control operations. Traces retain a labelled first-six/last-six event sample.

## Failed attempts and repairs

- The first network smoke attempt passed correctness but stopped at capability
  preflight: Docker reported `CAP_NET_ADMIN`, while the script expected
  `NET_ADMIN`. The containers already had the capability. The script now normalizes
  that prefix. No qdisc mutation occurred in the rejected attempt; a separate LAN
  reset was verified and the failed directory is retained.
- The first three 100-completion LAN repetitions each reached **63 completions and
  137 `CAPACITY_EXHAUSTED` failures**, hitting the 200-attempt ceiling. One warm-up
  plus 63 closed sessions filled the default 64 active-plus-tombstone records.
  Their caches were reclaimed, but IDs remained protected for the 30-second RPC
  replay window. The default now permits 4,096 bounded records; replay retention
  and hard capacity rejection remain. A new regression closes 100 sessions and
  verifies protected duplicate IDs. All three failed runs remain in the summary.
- That runner was interrupted during its last cleanup, so its final summary was
  absent. It is labelled interrupted, not plan-only or successful. A separately
  recorded reset confirmed all four queues were unshaped.
- Review found graceful coordinator shutdown could wait 40 seconds without
  observing the 15-second compute cancellation deadline. The supervisor now
  consumes control frames while draining; a real child-process regression covers
  a newly published cancellation deadline after SIGTERM.
- Reset previously preflighted all targets together. A stopped worker could
  prevent reset on healthy services. Cleanup now attempts each target independently,
  preserves inference and reset errors separately, and writes exclusive evidence.
  An actual WAN-shaped test stopped worker 2: the helper reported that failure
  and verified `noqueue` on workers 1/3 and the coordinator. Restart and final
  reset verified all four. Mocked tests also reject overwriting evidence before
  any reset callback runs.
- The first final-image repetition completed 102/102 requests, then the runner's
  reset wrapper failed because its PowerShell closure did not retain the shaper
  path. The runner correctly stopped the matrix and saved failed reset evidence.
  A manual reset verified all four queues. The wrapper now receives explicit
  paths/parameters and has a mocked-shaper regression through the actual callable
  used by the runner. That incomplete repetition is retained separately.
- A deliberately unavailable coordinator endpoint produced an explicit failed
  validation report with zero comparisons. It is retained as a negative test.

## Limits and remaining work

The declared full matrix has 48 configurations and three repetitions each (144
runs): prompt lengths 128/1,024, concurrency 1/3/8, separate delay and rate profiles,
and the combined profile. Only the selected configurations reported here were
collected. A generated full plan was checked for configuration/repetition coverage;
it was not executed. A full performance envelope and separate-device measurements
are still required for P3.

All processes share this laptop's CPU, RAM and kernel. Thermal state was unmeasured;
CPU quotas are not dedicated cores. Offline tests overlapped initial correctness/
early smoke work; the final repeated measurement ran without a test container.
Memory peaks are container-lifetime observations, not isolated per-case peaks.
Coordinator/worker loading times, parameter bytes, RSS and cgroup peaks are in the
summary. The coordinator retains 16,384,256 parameter bytes, while workers retain
787,968 / 787,968 / 525,312 bytes; this tiny model is dominated by its input/output
components. Cache ownership is distinct from allocator-retained process memory.

The private lab trusts every service and has no RPC authentication or encryption.
It does not implement GPU execution, peer discovery, replay recovery, reciprocal
credits or a public deployment. Historical Petals measurements remain labelled by
their older software and topology; no matched cross-runtime speed claim is made.
